# 04 · Actor 与 Service 到底是什么关系（重点篇）

## 你将学到

你最大的困惑：**"你说 actor 是 service，那为什么 service 又要交给 actor？"**
读完这篇你会明白：**Service 是"岗位/职责"，Actor 是"这个岗位的运行方式"。**

---

## 1. 先分清两个词

| 词 | 是什么 | 举例 |
| --- | --- | --- |
| **Service（服务）** | **业务概念**：一个职责单元 | gateway（接入）、login（鉴权）、world（世界） |
| **Actor** | **运行/隔离机制**：引擎提供的执行容器 | "一个有独立内存、只收消息、串行处理的执行体" |

**它们不是两个东西，而是"同一个东西的两个视角"**：
你写的 **service**，引擎用一个 **actor** 来运行它。

> 不是"service 交给 actor"这种被动动作；而是"**一个 service 就是一个 actor**"。
> 就像"前台"这个**岗位**，是用"**一名员工**"来承担的——岗位是职责，员工是执行者。

## 2. 用一个公司类比

- **Service = 岗位**：前台、仓库管理员、财务。
- **Actor = 这名员工的工作方式**：
  - 有自己的**办公室**（独立状态，别人不能进去乱翻）；
  - 只通过**纸条（消息）**沟通，不能直接抢别人桌上的东西；
  - **一次只处理一张纸条**（串行，不会同时干两件事）；
  - 有**工号/名字**（可被寻址）。
- **引擎 = 公司制度**：给每个岗位分配办公室和一条工作线（线程），并规定"只能递纸条"。

## 3. 为什么非要 Actor？普通对象不行吗？

服务器要同时满足四件事，普通对象做不到：

| 需求 | Actor 怎么解决 |
| --- | --- |
| **并发不打架** | 每个 actor 串行处理自己的消息 → 不用锁 |
| **隔离** | 每个 actor 独立内存/独立崩溃域 → 一个出问题不连累别人 |
| **可分布** | actor 有地址（名字/节点）→ 可以搬到另一台机器 |
| **可控内存** | 每个 actor 独立记账 → 可设内存上限 |

一句话：**Actor 是"让对象能安全地并发、隔离、分布"的容器。**

## 4. 在 Actor 里，你照样写 OO

你写业务代码时，还是用 table + 方法：

```lua
-- world.lua：这就是一个"对象"，只是它住在一个 actor 里
local entities = {}
function commands.move(self, uid, x, y)
    local e = entities[uid]
    e.x, e.y = x, y          -- 直接改自己的状态，安全（串行）
    return true
end
```

**唯一的区别**：外面的人**不能**直接 `world.entities[uid].x = ...`，
只能**发消息**：

```lua
router.call("world", "move", uid, x, y)   -- 递纸条给 world actor
```

actor 内部你怎么写都行（OO/过程式），因为**没有别人能同时动你的内存**。

## 5. "串行"是什么意思，为什么这么香

每个 actor 的消息队列像一条传送带，**一次只处理一条**：

```
world actor 的消息队列:
  [ MOVE uid=1 ] [ MOVE uid=2 ] [ ENTER uid=3 ] ...
        ↑ 依次处理，绝不并发
```

于是：
- 你**永远不用考虑"两个玩家同时改 entities"**——它们自动排队。
- 不需要锁、不需要担心数据竞争。
- 代价：**一个 actor 的处理能力有上限**（一条线程串行）→ 太大就**分片**（第 8 篇）。

## 6. unique 与普通 actor

| | 普通 actor | `unique` actor |
| --- | --- | --- |
| 跑在哪 | Tokio 线程池里的一个任务 | **独占一条 OS 线程** |
| 接收 | 异步 | 阻塞式接收 |
| 特点 | 省资源、可很多 | 确定性强、串行 |
| 本仓库 | （少用） | gateway/login/lobby/world/admin 都用它 |

为什么参考服务都用 unique？因为它们各自持有独立状态、要求严格串行、且需要按名字寻址。

## 7. 一张图收束

```
你写的（业务视角）              引擎跑的（运行视角）
─────────────────              ─────────────────
service "world"        ===>    actor：独立 lua_State + 消息队列 + 一条线程
  - entities 表                  - 串行处理消息
  - move/enter 命令              - 有名字 "world"，可被 router 寻址
  - 只通过消息被调用             - 独立内存、可设上限
```

## 8. 回答你的原话

> "你说 actor 是 service，那 service 为什么又要交给 actor？"

- 不是"交给"。是 **service 这个业务单元，由引擎实现成一个 actor 来运行**。
- **Service 是"要做什么"（职责）；Actor 是"怎么跑"（隔离 + 串行 + 可寻址）。**
- 你只需要关心写 service（业务）；actor 是引擎给你的"安全运行环境"。

## 8. 把"虚名词"落到代码对象

你嫌这些词虚——那就一个个对上代码：

| 虚名词 | 代码里是什么对象 | 怎么产生 / 怎么用 |
| --- | --- | --- |
| **服务 service** | 一个 Lua 脚本 + 一个逻辑名（`gateway.lua` / "gateway"） | 你写的业务文件，用 `service.run({name=...})` 跑 |
| **实例 instance** | 引擎里一个 **actor**（一个整数 id + 独立 `lua_State`），名字唯一 | `moon.new_service({name="lobby_1", source=...})` 创建并返回 id |
| **节点 node** | 一个**进程** + 一个整数 `node_id` | 启动时传入；对应 `topology.nodes[node_id]` |
| **组 group** | 一张表 `{ lobby = {"lobby_1","lobby_2"} }` | 写在拓扑里；`router` 用它轮询 |
| **actor** | 运行单元（id + lua_State + 消息队列） | 由 `moon.new_service` 创建；`moon.id` 可取自己的 id |
| **逻辑名 vs 实例名** | `"lobby"`（逻辑）→ 组指向 `"lobby_1"/"lobby_2"`（实例） | 业务只写逻辑名 `router.call("lobby", ...)` |

**关系链**（背下来）：

```
进程 = 节点（一个 node_id）
节点 里住着 很多 actor
一个 actor = 一个服务实例（有唯一 name）
一个"逻辑服务"（如 lobby）可以对应多个实例（lobby_1/lobby_2），用【组】把它们绑在一起
拓扑 决定：哪些实例跑在哪个节点、定义了哪些组
```

> 所以"服务/实例/组/节点"都不是运行时对象，而是**视角**：
> - 看**职责**叫"服务"；看**具体跑起来的那个**叫"实例"（= actor）；
> - 看**机器**叫"节点"（= 进程）；看**一组实例**叫"组"（= 一张表）。

## 动手

   "给这个 actor 装上消息处理回调"。

## 记住这句

> **Service = 岗位（业务）；Actor = 员工（运行方式：独立内存、只收消息、串行处理、可寻址）。**
> 一个 service 就是一个 actor。
