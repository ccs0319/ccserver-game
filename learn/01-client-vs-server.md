# 01 · 从客户端思维到服务器思维

## 你将学到

为什么"客户端里管对象"和"服务器里管对象"是两件不同的事，以及需要新增哪些观念。

---

## 1. 客户端：你在管理"副本"

在客户端里，你有一个玩家对象、一堆 NPC、子弹、特效……它们大多是为了**表现**：

- 位置、动画、血量——**用来画**。
- 你几乎可以随便改它们，因为**只有你一个人**在看这个屏幕。
- 掉了重连，重新拉一份数据就行。

**关键：客户端里的对象，本质是"真相的副本/投影"。**

## 2. 服务器：它持有"真相"

服务器上也有玩家对象、怪物对象，但意义完全不同：

- 它们是**权威数据**：谁在哪、多少血、背包有什么——**服务器说了算**。
- 客户端只是收到"结果"再画出来。
- 多个客户端**同时**操作同一批对象：两个玩家抢同一个宝箱、一个人被攻击、好友上下线。

一句话：**客户端负责"表现"，服务器负责"真相"。** 这叫 **server-authoritative（服务器权威）**。

> 为什么不能让客户端算？因为客户端不可信（可以改内存、改包）。服务器必须自己算、
> 自己校验。这就是"外挂"为什么打不到服务器数据。

## 3. 你已有的 OO 思维，哪些能用

| 客户端里 | 服务器里 | 能用吗 |
| --- | --- | --- |
| 玩家对象有位置/血量 | 一样有 | ✅ 直接用 |
| 对象之间互相调用方法 | **不能直接调**，要发消息 | ⚠️ 要换方式 |
| 每帧更新所有对象 | 由"收到消息/定时器"驱动 | ⚠️ 要换驱动方式 |
| 单线程主循环 | 多玩家并发，必须隔离 | ❌ 要新学 |

**最大的三个新问题**：
1. **并发**：成百上千玩家同时动，怎么不打架？
2. **隔离**：一个玩家/一个功能出问题，怎么不拖垮全部？
3. **分布**：一台机器不够了，怎么扩到多台？

## 4. 从"一个对象"到"一个服务器"

客户端里你可能写：

```cpp
class Player { vec3 pos; int hp; void Move(vec3 d){ pos += d; } };
```

服务器里，位置/血量还是这样存，但：

- 谁来调用 `Move`？→ **客户端发来一条"移动"消息**，服务器收到后才改。
- 改完要通知谁？→ 视野内的其它玩家（AOI）。
- 两个玩家同时改？→ 需要**串行**（排队）处理，避免数据竞争。

所以服务器需要一套机制：**把"调用对象方法"变成"投递消息 + 串行处理"**。这套机制就是
**Actor 模型**（见第 4 篇）。

## 5. 服务器对象的生命周期更长、更危险

- 服务器**长期运行**（数天/数月），内存泄漏、状态累积都是问题。
- 服务器崩了 = **所有玩家掉线**，所以要"故障隔离"（一个模块崩不影响别的）。
- 服务器状态**要持久化**（存数据库），重启后能恢复。

## 6. 把它映射到本仓库

| 概念 | 本仓库对应 |
| --- | --- |
| 玩家/怪物对象 | `world` 服务里的 `entities`（`lualib/ccserver/services/world.lua`） |
| 客户端发消息 | gateway 解析的协议帧（`ccserver/protocol.lua`） |
| "串行处理对象" | 每个服务是一个 **actor**（第 4 篇） |
| 对象数据持久化 | `moon.db` + `moon.db.migration`（第 9 篇） |
| 多玩家并发隔离 | 服务拆分 + actor 隔离（第 4、5 篇） |

---

## 动手

1. 打开 `lualib/ccserver/services/world.lua`，看 `entities` 表和 `move` 命令——
   这就是服务器版的"玩家对象 + 移动方法"，只是**通过消息调用**。
2. 想想你客户端里的"背包"对象：如果搬到服务器，哪些字段是"真相"，哪些只是"表现"？

## 记住这句

> **客户端管表现，服务器管真相；服务器要解决并发、隔离、分布三件事。**
