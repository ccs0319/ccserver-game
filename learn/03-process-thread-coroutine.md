# 03 · 进程 / 线程 / 协程 与并发

## 你将学到

服务器为什么"单进程多线程"，为什么还要"协程/异步"，以及这跟"很多玩家同时在线"有什么关系。

---

## 1. 三个层次，从小到大

| 名称 | 是什么 | 类比 |
| --- | --- | --- |
| **进程** | 操作系统分配资源的最小单位（内存、句柄）。彼此隔离。 | 一栋独立的房子 |
| **线程** | 进程内真正被 CPU 调度的单位，共享进程内存。 | 房子里的一个工人 |
| **协程** | 程序自己管理的"轻量任务"，切换成本极低。 | 工人的一张待办清单 |

- 一个进程可以有多个线程；一个线程上可以跑成千上万个协程。
- **线程切换贵（要进内核），协程切换便宜（只是存/取一下上下文）。**

## 2. 客户端的模型：单线程主循环

客户端一般是这样：

```
while (running) {
    pollInput();
    update(dt);      // 更新所有对象
    render();        // 画
}
```

**只有一个线程**，你改对象很安全（没人跟你抢）。这让你觉得"管对象"很简单。

## 3. 服务器为什么不能照抄

服务器要同时服务**很多玩家**。如果照抄"一个线程跑所有人"，会卡：
- 一个玩家的逻辑慢了，所有人一起卡。
- 但"一个玩家一个线程"也不行：几万玩家 = 几万线程，系统直接崩（线程太贵）。

**服务器的解法：**
1. **少量线程吃满多核**（比如 8 核就 8 个线程）。
2. 每个线程上跑**很多"任务"**，用**异步/协程**在"等待"时切换。

## 4. 关键概念：等待时要"让出"，不要"堵住"

服务器大量时间花在**等待 I/O**：等数据库、等别的服务、等网络。

- **同步阻塞**：一个线程等 DB 返回时，啥也不干 → 线程被浪费。
- **异步/协程**：等 DB 时，把这个协程挂起，线程去跑别的协程；DB 回来了再唤醒它。

这就是"异步"的全部意义：**用少量线程，同时扛住大量"正在等待"的任务。**

在本仓库里，`moon.sleep / moon.wait / router.call / db:query` 都会**挂起当前协程**，
把线程让给别人——所以你能"边等边服务其它玩家"。

```lua
moon.async(function()          -- 开一个协程（任务）
    local rows = db:query(...)  -- 等待时，线程去服务别人
    router.call("world", ...)   -- 再等，再让出
end)
```

## 5. 那"多线程"为什么还重要

- 一个线程只能用一个 CPU 核。要**吃满多核**就得多个线程。
- 本仓库：主进程里有一个 **Tokio 多线程运行时**（跑网络/定时/异步任务），
  外加每条 `unique` 服务独占的 OS 线程。

## 6. 线程安全：为什么"共享内存"是大坑

多个线程同时改同一块内存 → **数据竞争**（结果不确定、崩溃）。
传统解法是**加锁**，但锁写多了又慢又容易死锁。

本仓库（和 Erlang/Akka 一样）选择：**不共享内存**。
- 每个服务（actor）有自己的 Lua 状态，**只在一个线程上串行跑**。
- 服务之间**只发消息**，不直接读写对方内存。
- 于是**几乎不需要锁**——这是这套框架最核心的省心点。

## 7. 本仓库里的具体分工

```
进程 moon_rs
├── 主线程 / Tokio 运行时线程池   → 网络、定时、异步 I/O、普通 actor
├── IO runtime（≤4 线程）         → 原生模块（DB/网络）的 I/O
└── unique actor 独占线程 × N      → 需要串行的关键服务（gateway/login/world…）
```

- **普通 actor**：跑在 Tokio 任务里（很多 actor 共享线程池）。
- **`unique` actor**：独占一条 OS 线程 + 阻塞式接收消息（简单、确定、串行）。

> 我们参考服务都用 `unique = true`，因为它们各自持有独立状态、要求串行。

## 记住这句

> **服务器 = 少量线程 + 大量协程；等待时让出线程；不共享内存、只发消息，从而绕开锁。**
