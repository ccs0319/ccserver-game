# 09 · 数据层与持久化

## 你将学到

游戏服务器的数据该存哪：内存、缓存、数据库各管什么；为什么不能每次都读数据库；表结构变了怎么办。

---

## 1. 三层数据

| 层 | 存什么 | 特点 | 本仓库 |
| --- | --- | --- | --- |
| **内存（actor 内）** | 正在玩的玩家实体、临时状态 | 最快，但**进程崩就没了** | world 的 `entities` |
| **缓存（Redis）** | 会话、排行、热数据、跨进程共享 | 快，有 TTL，可共享 | `moon.db` redis、`ccserver.session` |
| **数据库（SQL/Mongo）** | 账号、背包、订单等**要长期保存**的 | 慢，但**可靠、可查** | `moon.db` sqlx/mongo |

**原则**：**热数据在内存/缓存，冷数据/持久数据在数据库。** 永远不要每个操作都打数据库。

## 2. 为什么不能每次都读数据库

- 数据库一次查询可能几毫秒；一帧/一条消息就查一次 → 服务器立刻被拖垮。
- 所以玩法用**内存里的对象**算，只在**关键点**落库（比如退出、定时、交易）。

```
玩家移动 1000 次  → 只改内存（快）
玩家下线/定时     → 把内存里的最终状态写一次数据库（慢但少）
```

## 3. 缓存（Redis）为什么关键

- **跨进程共享**：多个 gateway/world 需要看同一份数据（会话、排行）。
- **快**：内存级，比数据库快几个数量级。
- **过期**：可以设 TTL，适合会话、验证码这类"过期即失效"的数据。

例：本框架的**会话属主**就放 Redis（`ccserver.session`），所以任何网关都能查到"谁在线"。

## 4. 持久化策略（什么时候写库）

| 策略 | 说明 | 适用 |
| --- | --- | --- |
| **即时写** | 每次变更立刻写库 | 交易、充值（不能丢） |
| **定时刷** | 每隔几秒/几十秒批量写 | 位置、经验（丢一点可接受） |
| **退出时写** | 下线时写一次 | 大部分玩家数据 |

通常**组合使用**：重要数据即时写，普通数据定时+退出写。

## 5. 事务与一致性

- 数据库的**事务**保证"要么全成功、要么全回滚"（比如扣钱+发货）。
- 本仓库 `moon.db` 支持 `:transaction({...})` 和 `:execute_transaction({...})`。
- 注意：**跨服务/跨进程**没有"全局事务"，要靠**幂等 + 重试 + 补偿**来保证最终一致。

## 6. 表结构会变：迁移（Migration）

游戏上线后经常要加字段、加表。直接改数据库很危险（线上数据不能重来）。
本仓库用**迁移**管理表结构变化：

```
assets/migration/0001_init.lua            # 建表
assets/migration/0002_add_created_at.lua  # 加字段
```

- 每个迁移文件按**版本号**顺序执行，只跑一次，记录在 `schema_migrations` 表里。
- 有**校验和**（改了已执行的迁移会被发现）、**并发锁**（多实例启动不会重复执行）、可**回滚**（`down`）。

## 7. 连接与健康

- 数据库连接是**有代价**的，要用**连接池**复用（本仓库由 Rust 侧管理池）。
- 要有**健康检查**（`db.health()`）——数据库挂了要能及时发现、降级。

1. `make db-up` 起本地 Redis/MySQL/PG，然后 `make test-db`。

## 记住这句

> **热数据在内存/Redis，持久数据在数据库；别每条消息都读库；用迁移安全地改表结构。**
